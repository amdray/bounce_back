## Факт из Java кода

В основном проходе карты при `ab=false` runtime-поворот отключен принудительно:

```java
k = (paramInt4 == 0) ? this.b[i] : paramInt4;
k = 0;
```

Источник: `original_code/bounce_back_s60.jar.src/g.java:624-625`.

Следствие:
- Для map-pass поворот/отражение в рантайме не выполняется.
- Рендер идет «как в текстуре», даже если у тайла есть `b != 0`.

## Вертикальные турбины сломаны уже в оригинале, и корень не в `lf`

Статус: подтверждено по первичному Java-источнику и по данным уровней.

Что важно не перепутать:
- Проблема относится не к большим кольцам и не к map-pass, а к front-тайлам турбины.
- Для "уровня 6 с единицы" это внутренний `L05`.

Что подтверждено:
- Горизонтальная турбина на `L05` собрана из `tileId` `52 54 56 59 66 69`.
- Вертикальная турбина на `L05` собрана из `tileId` `45 51 53 55 57 60 67 71`.
- В `lf` вертикальная турбина разложена корректно как `2x6`, флаг `0x80` у этих тайлов не используется.
- В `res/tf` у горизонтального набора `transform = 0`, а у вертикального набора у всех стоит `transform = 0x03`.
- Оригинальный front-pass в `h.java` действительно применяет этот `transform` через `DirectGraphics.drawImage(..., this.Z.p[b])`, поэтому вертикальная турбина в оригинале тоже визуально ломается.

Почему это не баг `lf`:
- Те же вертикальные `tileId` встречаются и в других уровнях (`L13`, `L18`, `L20`) с той же ориентационной логикой.
- Значит дефект общий для семейства front-тайлов, а не локальная ошибка одной карты.

Почему `level_flags_inspector.html` может выглядеть "правильно":
- Инспектор рисует raw-текстуру через `ctx.drawImage(...)` и не применяет runtime-поворот для этих front-тайлов.
- Поэтому он по сути показывает "как если бы `transform` был проигнорирован".

Практический вывод:
- В этом проекте баг оставлять не нужно: вертикальную турбину считаем подлежащей исправлению, даже если в оригинале она тоже визуально ломается.
- Это осознанное отклонение от parity ради визуально корректного результата.
- Править логично либо рендер front-pass, либо данные `res/tf` для вертикального семейства `45 51 53 55 57 60 67 71`.
- Горизонтальную турбину такой фикс не затрагивает, потому что у неё другой набор `tileId`.

## Транспонирование collision mask это намеренный паритет

Статус: подтверждено в этом репозитории.

Что выглядит как баг:
- В `src/level_loader.c` inline-маски тайлов выделяются и заполняются как `tile_mask[x][y]`.
- В коллизии они затем читаются как `tile_mask[mask_y][mask_x]`.

Почему это не нужно "исправлять":
- Это совпадает с первичным Java-источником: в `original_code/bounce_back_s60.jar.src/g.java` оригинал тоже пишет маски как `s[x][y]`, а в коллизии читает как `arrayOfBoolean[y][x]`.
- Значит, runtime-интерпретация маски транспонирована относительно порядка хранения в `/res/tf`.
- Данные ресурсов уже завязаны на это поведение. Диагонали, скосы и другие несимметричные маски фактически сохранены так, чтобы правильно работать именно с таким runtime-доступом.

Практическое правило:
- Не менять `tile_mask[mask_y][mask_x]` на `tile_mask[mask_x][mask_y]`, если одновременно не мигрируются формат ресурсов и все существующие данные масок.
- Считать это ограничением совместимости ресурсов, а не локальной ошибкой индексации.

## Магическое `+ 2` в вертикальном разрешении коллизии это часть паритета

Статус: подтверждено в этом репозитории.

Что выглядит подозрительно:

Почему это не нужно "улучшать":

Практическое правило:
- Не убирать и не нормализовать это смещение без полной сверки с Java-логикой по данному кейсу.
- Для pixel-perfect parity это следует считать значимой константой поведения.

## В Java-кампании не 22 обычных уровня, а 20 обычных + 1 скрытый + 1 help/demo path

Статус: подтверждено по первичному Java-источнику.

Что легко перепутать:
- По ресурсам можно увидеть индексы до `21` включительно и сделать вывод, что в обычной игре есть `22` последовательных уровня.
- Это неверно для campaign flow.

Что подтверждено:
- Обычный level select ограничен `21` пунктом через `Math.min(21, this.s)`.
- После завершения уровня `20` Java показывает special congratulation screen.
- Если текущий run был начат с уровня `1`, после этого экрана игра ещё пускает на скрытый уровень `21`.
- Если run был начат не с уровня `1`, после этого экрана игра сразу завершает прохождение и переходит к итоговому экрану.
- Resource level index `21` не относится к обычной кампании: он используется отдельным help/demo path.

Практический контракт:
- Для обычного выбора уровней корректно считать `LEVEL_COUNT = 21`.
- Нормальная progression в Java такая: `1..20 -> congratulation screen -> 21 -> final`, но только если run стартовал с уровня `1`.
- Для runs, начатых с любого другого уровня, progression такая: `N..20 -> congratulation screen -> final`.
- Если считать с единицы все resource level indices, картина такая: `1..20` это обычная кампания, `21` это скрытый финальный уровень, `22` это help/demo path.

## Finding «двойная инверсия j портит toward_surface» — Неактуально

Статус: проверено и опровергнуто (15.03.2026).

Проверяемое утверждение:
- «В `src/player.c` логика `gravity_down` неверна: `j` инвертируется дважды, из-за чего `toward_surface` вычисляется неправильно по сравнению с Java.»

Что на самом деле происходит:

Обе инверсии — это намеренный паттерн **нормализации с восстановлением**, идентичный Java:

```
// A: нормализация — приводим j к единой системе (j>0 = к поверхности)
if (this.p) j = -j;                                   // Java a.java ~692
if (p->gravity_down) j = -j;                          // C   player.c:781

// B: вычисляем step/toward_surface на нормализованном j
byte b1 = sign(j);                                     // Java a.java:695
int step_y = sign(j);  toward_surface = (step_y > 0); // C   player.c:783,787

// C: восстанавливаем j для дальнейшей физики
if (this.p) j = -j;                                   // Java a.java ~700
if (p->gravity_down) j = -j;                          // C   player.c:789
```

Две инверсии не «отменяют» `toward_surface` — между ними находятся вычисления `step_y`, которые берут знак уже нормализованного `j`. После точки C `j` возвращается в исходное состояние для дальнейшей физики (bounce, position update).

О странном выражении `bool3` в декомпиляте:
- Строка 696 a.java: `boolean bool3 = ((b1 && !this.p) || (b1 && this.p)) ? true : false;`
- Это **ошибка декомпилятора** — в Java нельзя записать `byte && boolean`. Байткод не содержит такой конструкции.
- Проверка по байткоду реального `original_code/bounce_back_s60.jar` через `javap` даёт точную форму:

```java
bool3 = (b1 >= 0 && !this.p) || (b1 <= 0 && this.p)
```

- Для ненулевого шага это упрощается до:

```java
bool3 = (b1 > 0 && !this.p) || (b1 < 0 && this.p)
```

- После первой инверсии `j` это и есть предикат «движение к поверхности».
- В C это корректно выражено как `toward_surface = (step_y > 0)`, потому что `step_y` берётся уже после той же нормализации `j`.
- Нулевой шаг в байткоде тоже покрыт: при `b1 == 0` `bool3` становится true, но этот случай не меняет семантику collision-path, потому что вертикальный sub-step отсутствует.

## «Странности» player.c — это Java-парные фичи, а не баги портинга

Статус: подтверждено по `a.java` + байткод `a.javap.txt` (17.03.2026).

Пять паттернов из `player.c` были проверены против оригинального Java-кода и байткода. Все пять — намеренное поведение оригинала.

### 1. `is_inverted = false` при создании большого мяча (`player_create`)

Что выглядит подозрительно:
- `player_create` устанавливает `is_inverted = false` даже если `is_large_ball = true`.
- `player_respawn` устанавливает `is_inverted = true` для большого мяча.
- Кажется, первая жизнь имеет неправильную физику.

Почему это не баг:
- Java `a(int,int,int)` (init): `this.I = false` — без условия на `paramInt3`.
- Java `e()` (respawn): `if (this.t) { a(11); this.I = true; }` — is_inverted только при respawn.
- Первая жизнь в Java тоже начинается без `is_inverted`. C-порт воспроизводит оригинал точно.

### 2. Правый конвейер: `i = 250` (не `i += 250`) и dead-code ветка

Что выглядит подозрительно:
- Левый конвейер аддитивен: `i -= (tile == 76) ? 125 : 250;`.
- Правый конвейер полностью перезаписывает: `i = 250;`.
- После `i = 250` ветка `else if (i < 0)` — мёртвый код.

Почему это не баг:
- Java `a.java` строка 1419: `i = 250;` — жёсткое присваивание, без `+=`.
- Та же dead-code ветка `else if (i < 0)` присутствует в Java.
- Байткод подтверждает: offset `6241` → `sipush 250; istore_2` (присваивание, не сложение).
- Асимметрия левых/правых конвейеров — намеренный игровой дизайн оригинала.
- Нет варианта «половинной силы» для правых конвейеров — тоже оригинал: Java не имеет аналога `tile == 76` для правого набора.

### 3. Respawn offset = 8 всегда, даже для большого мяча

Что выглядит подозрительно:
- `player_create` использует `offset = is_large_ball ? 12 : 8`.
- `player_respawn` использует `offset = 8` — без проверки размера мяча.
- Кажется, большой мяч после смерти позиционируется со сдвигом на 4px.

Почему это не баг:
- Java `h.java` (create): `else { i += 12; j += 12; }` — offset 12 только при первом создании.
- Java `e()` (respawn): `this.D = this.H * 16 + 8; this.i = this.n * 16 + 8;` — всегда 8.
- Расхождение create (12) vs respawn (8) — это оригинальная непоследовательность Java, не ошибка портинга.

### 4. Kill-tile проверка по `hits->x[0]`, а не по текущему `hits->x[h]`

Что выглядит подозрительно:
- В конвейерном кейсе `84/108/83` после неудачного сдвига `+1` killer-тайл проверяется по `hits->x[0]`, а не по текущему индексу цикла.

Почему это не баг:
- Java `a.java` строки 1198–1199: `i7 = this.v.P[0]; i8 = this.v.Y[0];` — явный индекс `[0]`.
- C-порт с `hits->x[0]` — точная Java-парность.

### 5. Разная логика id_logic объектов в вертикальном и горизонтальном проходах

Что выглядит подозрительно:
- Вертикальный проход: `ao[k] == 0` → `is_stone ? 200 : 201`.
- Горизонтальный проход: `ao[k] == 0` → `201` (без проверки `is_stone`).
- Кажется, каменный мяч при горизонтальной коллизии с type-0 объектом неправильно погибнет.

Почему это не баг:
- Java вертикальный проход (`a.java` строки 735–750): `case 0: i5 = this.F ? 200 : 201;` — с `is_stone`.
- Java горизонтальный проход (`a.java` строки 1478–1490): `case 0: i4 = 201;` — без `is_stone`.
- Асимметрия — оригинальный Java-дизайн. C-порт воспроизводит оба прохода точно.
