# Интересные находки

## Транспонирование collision mask это намеренный паритет

Статус: подтверждено в этом репозитории.

Что выглядит как баг:
- В `src/level_loader.c` inline-маски тайлов выделяются и заполняются как `tile_mask[x][y]`.
- В коллизии они затем читаются как `tile_mask[mask_y][mask_x]`.

Почему это не нужно "исправлять":
- Это совпадает с первичным Java-источником: в `original_code/bounce_back_s60.jar.src/g.java` оригинал тоже пишет маски как `s[x][y]`, а в коллизии читает как `arrayOfBoolean[y][x]`.
- Значит, runtime-интерпретация маски транспонирована относительно порядка хранения в `/res/tf`.
- Данные ресурсов уже завязаны на это поведение. Диагонали, скосы и другие несимметричные маски фактически сохранены так, чтобы правильно работать именно с таким runtime-доступом.

Практическое правило:
- Не менять `tile_mask[mask_y][mask_x]` на `tile_mask[mask_x][mask_y]`, если одновременно не мигрируются формат ресурсов и все существующие данные масок.
- Считать это ограничением совместимости ресурсов, а не локальной ошибкой индексации.

## Магическое `+ 2` в вертикальном разрешении коллизии это часть паритета

Статус: подтверждено в этом репозитории.

Что выглядит подозрительно:
- В `src/player.c` при одном из сценариев вертикального разрешения коллизии используется смещение вида `top + obj_h + p->half_height + 2`.
- Без контекста это выглядит как локальный хардкод.

Почему это не нужно "улучшать":
- В первичном Java-источнике в том же месте есть прямой аналог: `int i11 = i9 + 11 + this.c + 2;`.
- То есть добавка `+ 2` является частью оригинального поведения, а не портировочным мусором.

Практическое правило:
- Не убирать и не нормализовать это смещение без полной сверки с Java-логикой по данному кейсу.
- Для pixel-perfect parity это следует считать значимой константой поведения.

## В Java-кампании не 22 обычных уровня, а 20 обычных + 1 скрытый + 1 help/demo path

Статус: подтверждено по первичному Java-источнику.

Что легко перепутать:
- По ресурсам можно увидеть индексы до `21` включительно и сделать вывод, что в обычной игре есть `22` последовательных уровня.
- Это неверно для campaign flow.

Что подтверждено:
- Обычный level select ограничен `21` пунктом через `Math.min(21, this.s)`.
- После завершения уровня `20` Java показывает special congratulation screen.
- Если текущий run был начат с уровня `1`, после этого экрана игра ещё пускает на скрытый уровень `21`.
- Если run был начат не с уровня `1`, после этого экрана игра сразу завершает прохождение и переходит к итоговому экрану.
- Resource level index `21` не относится к обычной кампании: он используется отдельным help/demo path.

Практический контракт:
- Для обычного выбора уровней корректно считать `LEVEL_COUNT = 21`.
- Нормальная progression в Java такая: `1..20 -> congratulation screen -> 21 -> final`, но только если run стартовал с уровня `1`.
- Для runs, начатых с любого другого уровня, progression такая: `N..20 -> congratulation screen -> final`.
- Если считать с единицы все resource level indices, картина такая: `1..20` это обычная кампания, `21` это скрытый финальный уровень, `22` это help/demo path.

## Раздельные ветки физики скосов это не мусорный дубль

Статус: подтверждено в этом репозитории.

Что выглядит подозрительно:
- В `player.c` есть две очень похожие ветки для приземления на левые и правые скосы.
- На первый взгляд кажется, что логику squash, bounce_state и grounded можно свернуть в общий helper.

Почему это не нужно "упрощать":
- В первичном Java-источнике эти ветки тоже раздельные.
- Они не полностью идентичны: различаются пороги, знак горизонтальной коррекции и направления вспомогательных сдвигов.
- Попытка схлопнуть их в "общую" функцию повышает риск незаметно изменить parity-поведение на пограничных скоростях и направлениях.

Практическое правило:
- Не рефакторить эти ветки ради уменьшения дублирования, если нет очень жёсткой регрессионной проверки.
- Для pixel-perfect parity лучше сохранять структуру ветвления близкой к Java.

## Повтор обработки тайлов 97/98 и 101/102 это часть структуры оригинала

Статус: подтверждено в этом репозитории.

Что выглядит подозрительно:
- В `player.c` логика сбора и преобразования больших колец для `97/98` и `101/102` выглядит повторённой в нескольких ветках движения.
- Возникает соблазн вынести это в общий helper и убрать дубли.

Почему это не нужно "абстрагировать":
- В первичном Java-источнике аналогичная обработка тоже повторяется отдельно внутри вертикального и горизонтального проходов.
- Повтор привязан к разным вариантам резолва коллизии после смещения игрока, а не только к самому факту "собрать кольцо".
- Схлопывание может незаметно изменить момент, в который происходит сбор или перестройка соседних тайлов.

Практическое правило:
- Не выносить эту логику в абстрактный helper только ради уменьшения объёма кода.
- Если и менять структуру, то только при полной сверке порядка операций с Java.

## Поиск свободного места при смене спрайта это копия Java-алгоритма

Статус: подтверждено в этом репозитории.

Что выглядит подозрительно:
- В `player_change_sprite()` есть большой поиск свободного места: сначала по `dx`, потом по `dy`, затем по диагоналям.
- На первый взгляд это может выглядеть как поздняя самодеятельная "подпорка".

Почему это не нужно "упрощать":
- В первичном Java-источнике этот же алгоритм присутствует в той же последовательности: вправо/влево, затем вниз/вверх, затем четыре диагональных направления.
- Это часть оригинального поведения при смене размеров и спрайта игрока, а не лишняя защита.

Практическое правило:
- Не заменять этот код на "более умный" или "более короткий" вариант.
- Если цель проекта это parity с оригиналом, алгоритм должен оставаться структурно тем же.

## Альтернативный ввод сейчас не нужен проекту

Статус: зафиксировано как сознательная граница задачи.

Что выглядит как возможное улучшение:
- В `src/input.c` при отсутствии `SDL_GameController` функция `input_update()` сразу выходит.
- Для desktop bring-up это могло бы оправдывать keyboard fallback или явное обнуление `Input`.

Почему это сейчас не приоритет:
- Целевая платформа проекта это PSP, где основной ввод встроен и альтернативная схема управления не нужна.
- Для текущей цели важнее parity с оригинальным управлением, а не расширение набора источников ввода для desktop-режима.
- То есть замечание про отказоустойчивость к desktop/hot-unplug можно считать технически верным, но не поводом тащить в проект лишний альтернативный input-path.

Практическое правило:
- Не добавлять keyboard fallback или дополнительную desktop-схему ввода только "на всякий случай".
- Возвращаться к этой теме только если появится отдельная цель поддерживать non-PSP режим как полноценный сценарий.

## HUD-иконка жизней сознательно адаптирована, это не случайный баг

Статус: зафиксировано как осознанное отклонение.

Что может выглядеть подозрительно:
- В оригинале HUD рисует lives-индикатор через `S[1]` с клипом `12x16`.
- В C-порте этот же lives-слайс по-прежнему берётся из `g_hud_lives_strip`, но дополнительно рядом рисуется отдельная иконка мяча другой текстурой.

Почему это не нужно автоматически считать ошибкой:
- Это не случайный fallback и не потерянный ресурсный контракт, а сознательная адаптация под текущий экран и HUD-layout.
- Исходный Java-путь опирается только на клип из `S[1]`, без отдельной дополнительной иконки мяча.
- В порте отдельная иконка мяча была добавлена намеренно как адаптация HUD-подачи на PSP, при этом слайс `S[1]` сохранён.

Практическое правило:
- Не заводить это как баг только потому, что C-порт не рисует HUD-жизни тем же способом, что Java.
- Возвращаться к этому только если появится отдельная цель восстановить именно исходный HUD-asset/layout без адаптации.

## HUD-кольца без overlap это сознательная PSP-адаптация

Статус: зафиксировано как осознанное отклонение.

Что может выглядеть подозрительно:
- В оригинале HUD рисует `S[2]` с overlap по X: следующий значок сдвигается всего на `6px`.
- В C-порте те же кольца из `ic[2]` раскладываются без overlap, с полным шагом по ширине значка.

Почему это не нужно автоматически считать ошибкой:
- Это не подмена ресурса и не fallback на другой ассет: используется тот же HUD-спрайт колец `ic[2]`.
- Изменена только раскладка по экрану.
- На исходном экране `176px` overlap был нужен из-за дефицита горизонтального места.
- На PSP при `480px` экран позволяет разместить кольца без сжатия, поэтому отсутствие overlap было сделано намеренно.

Практическое правило:
- Не заводить это как parity-баг автоматически.
- Считать это отдельным адаптационным решением HUD-layout, а не поломкой ресурсного контракта.
