Продолжил сверку. Нашёл несколько реальных расхождений; критичных freeze-loop пока не вижу.

**Расхождения**
- **Stale center tile до state-transition**  
  Java: сначала применяет `A/r/a/q` state machine, потом читает тайл центра: `original_code/bounce_back_s60.jar.src/a.java:617`, `original_code/bounce_back_s60.jar.src/a.java:652`.  
  C: читает `center_tile`/`tile_flag80` до `timer_a` transitions: `src/player.c:891`, `src/player.c:898`.  
  Проявление: кадр окончания inflate/deflate/squash рядом с flag80/конвейером/пауэрапом.  
  Опасность: **серьёзно** — один тик неверной гравитации/силы тайла может менять траекторию.

- **Horizontal force uses pre-vertical tile**  
  Java: в vertical loop обновляет `i1` по новому `n`: `original_code/bounce_back_s60.jar.src/a.java:701`, `original_code/bounce_back_s60.jar.src/a.java:704`, потом использует этот `i1` для горизонтальных конвейеров: `original_code/bounce_back_s60.jar.src/a.java:1411`.  
  C: использует старый `center_tile`, взятый до vertical movement: `src/player.c:893`, `src/player.c:1708`.  
  Проявление: мяч за тик падает/поднимается в другой тайл, особенно на конвейер/толчковый тайл.  
  Опасность: **серьёзно** — видимое отличие скорости/траектории.

- **Stone/object overlap bounds differ on Y**  
  Java moving objects use `e.J` для верхней Y-границы, не `e.c`: `original_code/bounce_back_s60.jar.src/h.java:1115`, `original_code/bounce_back_s60.jar.src/h.java:1116`.  
  C uses `half_height` for Y bounds: `src/main.c:577`, `src/main.c:579`.  
  Проявление: stone-ball блокирует/не блокирует moving object иначе, если sprite width/height отличаются.  
  Опасность: **серьёзно** — может изменить движение платформ/прессов и застревания.

- **Exit door opens/checks one tick differently**  
  Java checks exit inside player update before door animation tick/render: `original_code/bounce_back_s60.jar.src/a.java:607`; door `o` flips later in render path: `original_code/bounce_back_s60.jar.src/h.java:664`.  
  C ticks and checks door before `player_update`: `src/main.c:585`, `src/main.c:586`, `src/main.c:644`.  
  Проявление: стоя в двери в момент открытия, C может завершить уровень на тик раньше.  
  Опасность: **косметично/слабо серьёзно** — gameplay timing, не freeze.

- **God mode prevents Java deaths**  
  Java `k()` всегда запускает смерть: `original_code/bounce_back_s60.jar.src/a.java:187`.  
  C suppresses death when `god_mode`: `src/player.c:366`, toggled by `L+R`: `src/player.c:883`.  
  Проявление: любые spikes/enemies/crush при включённом cheat.  
  Опасность: **серьёзно** для parity, но gated intentional cheat.

- **Out-of-map direct tile reads are guarded in C**  
  Java direct `R[n][m]` can throw if center leaves map: `original_code/bounce_back_s60.jar.src/a.java:654`.  
  C `level_get_tile` returns `0` out of bounds: `src/level_loader.c:530`.  
  Проявление: только если мяч уже оказался за пределами карты.  
  Опасность: **серьёзно в аварийном состоянии**, иначе не проявляется.

**Итог**
- Самые опасные для физики: первые три.
- Я бы в первую очередь правил порядок sampling в `player_update` и Y-bound для `level_objects_tick`.
