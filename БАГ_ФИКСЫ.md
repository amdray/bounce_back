## Камера по X выходила за правую границу при уровне шириной в экран

Статус: исправлено.

Где было:
- [camera.c](/mnt/d/OneDrive/VSCodeProject/psp/bounce_back/src/camera.c)

Симптом:
- Для уровня шириной ровно `480px` (`30` тайлов по `16px`) `maxCameraX == 0`, но камера всё равно начинала двигаться вправо за игроком.
- Из-за этого справа появлялось пустое небо, хотя уровень уже закончился.

Причина:
- Старый код зажимал камеру сверху только при `maxCameraX > 0`:
  `if (cameraX > maxCameraX && maxCameraX > 0) cameraX = maxCameraX;`
- При `maxCameraX == 0` этот clamp не срабатывал вообще.

Что исправлено:
- Если `maxCameraX <= 0`, камера по X теперь жёстко ставится в `0`.
- Для широких уровней поведение осталось прежним: камера зажимается в диапазоне `0..maxCameraX`.

Практический эффект:
- Уровни шириной в экран больше не показывают пустоту справа из-за ложного смещения камеры.

## Каденция главного цикла не совпадала с оригиналом (SDL_Delay(50) после работы)

Статус: исправлено.

Где было:
- [main.c](src/main.c) — 6 мест с `SDL_Delay(50)` (все ветки стейт-машины: MENU, LEVEL_SELECT, LEVEL_COMPLETE, GAME_OVER, CONGRATULATIONS, GAME)

Симптом:
- Реальный период кадра = время update+render + 50 мс. При любой ненулевой нагрузке CPU порт работал медленнее 20 тиков/с.
- Визуально: игра чуть медленнее оригинала, анимации и физика запаздывают.

Как в оригинальном Java:
- `h.java:811`: `this.aj = new f(this, 50)` → `f.java` делает `Timer.schedule(this, 0L, paramInt)`.
- Это Java `Timer` с fixed-delay семантикой: следующий тик планируется через 50 мс **от начала** текущего, а не после его завершения.
- Если `run()` занял W < 50 мс — следующий вызов через 50 мс от старта. Если W ≥ 50 — немедленно.

Причина:
- Порт делал `SDL_Delay(50)` после всей работы кадра, что давало период = W + 50 мс вместо ровных 50 мс start-to-start.

Что исправлено:
- В начале каждой итерации `while (running)` захватывается `tick_start = SDL_GetTicks()`.
- Все 6 `SDL_Delay(50)` заменены на: `{ uint32_t el = SDL_GetTicks() - tick_start; if (el < 50) SDL_Delay(50 - el); }`
- Если кадр занял ≥ 50 мс — sleep пропускается (как в Java Timer).

Что сознательно не менялось:
- VSync не добавлен — он не нужен для parity.
- Accumulator / интерполяция не внедрены — оригинал работает на чистых 20 Hz без разделения physics/render.
- `SDL_Delay(16)` в splash-скринах оставлен без изменений — он не относится к игровому циклу.

Практический эффект:
- Каденция порта теперь совпадает с оригиналом: ровные 50 мс start-to-start (20 Hz).
- По этой чистке удалено как минимум `43` строки кода.
  Это консервативная оценка: в число входят только явные удалённые строки (`collision.c`, `collision.h`, `player.h`, `main.c`, `menu.c`, `Makefile`), но не включены line-neutral механические переписывания вызовов и сигнатур в `player.c`.

## Восстановлен respawn от активированного checkpoint, а не только от старта уровня

Статус: исправлено.

Где было:
- [player.c](/mnt/d/OneDrive/VSCodeProject/psp/bounce_back/src/player.c)

Симптом:
- После смерти шар всегда возвращался в стартовую точку уровня.
- Активированные checkpoint-тайлы не влияли на respawn.

Причина:
- В C-порте `player_respawn()` уже использовал `spawn_tile_x/spawn_tile_y`, но эти поля обновлялись только при создании игрока.
- Логика активации checkpoint из Java для tile `34` была потеряна.

Как в оригинальном Java:
- В `a.java` tile `34` не только даёт очки, но и обновляет checkpoint-поля `this.n` / `this.H`.
- Предыдущий активный checkpoint при этом очищается, если он был в состоянии `35`.

Что исправлено:
- При сборе tile `34` теперь обновляются `spawn_tile_x/spawn_tile_y`.
- В respawn-state переносится размерный флаг checkpoint (`spawn_is_large`), как в текущем контракте игрока.
- Предыдущий активный checkpoint очищается, если он был в состоянии `35`.

Практический эффект:
- После смерти шар возвращается на последний активированный checkpoint, а не на старт уровня.

## Восстановлен Java-fallthrough для special tiles, из-за которого ломался насос

Статус: исправлено.

Где было:
- [player.c](/mnt/d/OneDrive/VSCodeProject/psp/bounce_back/src/player.c)

Симптом:
- С насоса нельзя было нормально прыгнуть.
- Тайлы `11/15/18/22/26/39` вели себя как “мгновенно обработанные”, без последующей обычной collision-логики.

Причина:
- В C-коде после `player_special_tile(...)` стоял ранний `resolved = true; break;`.
- В оригинальном Java для этих тайлов вызывается special-effect, а затем код намеренно проваливается в обычную collision/default-ветку.

Как в оригинальном Java:
- `a.java` для `case 11/15/18/22/26/39` вызывает `c(...)`, после чего продолжает выполнение collision-обработки в `default`.

Что исправлено:
- Убрано преждевременное завершение обработки для special-тайлов в двух collision-ветках.
- Добавлена явная пометка, что здесь нужен intentional fallthrough по Java-поведению.

Практический эффект:
- Насос снова работает как твёрдая специальная поверхность, и прыжок с него больше не блокируется.

## Continue больше не деградирует в resume-from-pause

Статус: исправлено и подтверждено в рантайме.

Где было:
- [main.c](/mnt/d/OneDrive/VSCodeProject/psp/bounce_back/src/main.c)

- После перезапуска игра не восстанавливала сохранённое состояние, хотя UI обещал именно это поведение.

Причина:
- Старый C-путь держал `has_save` только в памяти процесса.
- Persisted save/resume-контракт из Java `CrystalRMS` / `q` отсутствовал.

- `Continue` завязан на сохранённое состояние в `RecordStore("CrystalRMS")`.
- Отдельно различаются минимум два состояния: resume из игры и continue после завершения уровня.

Что исправлено:
- Добавлен PSP savedata-модуль для persisted continue-state.
- `Continue` в меню теперь зависит от реально загруженного save-state, а не только от паузы в текущем запуске.
- Реализовано восстановление из середины уровня с runtime-состоянием уровня и игрока.
- Реализовано continue-состояние после `Level Complete`.
- `New Game`, `Game Over` и `Congratulations` очищают continue-state.

Проверка:
- Сценарий подтверждён в эмуляторе: выход из уровня, закрытие игры, повторный запуск, `Continue` — игра открывается с того же места.

Практический эффект:
- По коду `Continue` снова соответствует resume-from-save, а не resume-from-pause.

Практический эффект:
- Campaign flow порта теперь соответствует подтверждённой Java-логике.
