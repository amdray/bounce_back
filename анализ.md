## Анализ производительности Bounce Back

### Лог: что реально происходит при старте

| Stage | Время |
|---|---|
| Сумма всех залогированных этапов | ~0.90 s |
| `hud_init` (самый тяжёлый) | 0.571 s |
| `present_loading_splash_for(..., SPLASH_PHASE_MS)` | **3.75 s** (намеренная пауза) |
| Второй `while (...< SPLASH_PHASE_MS)` в конце загрузки | **~3.75 s** |
| **startup.total** | **7.598 s** |

→ Из 7.6 секунд ~6.7 s — это **сознательные сплэш-задержки**, а не реальная работа. Реальная загрузка занимает **меньше секунды**.

### Критичные проблемы

#### 1. `fprintf(log, ...)` каждый игровой тик — main.c

```c
if (log) {
    if (input.right && !input.left) fprintf(log, "xSpeed=%d\n", ACCEL_NORMAL);
    if (input.left && !input.right) fprintf(log, "xSpeed=%d\n", -ACCEL_NORMAL);
    ...
}
```

В логе видно 80+ строк `xSpeed=18` — это **системный I/O-вызов каждые 50 ms** (каждый тик). `fprintf` без явного `fflush` всё равно флашит через libc при частых маленьких записях. На PSP это особенно болезненно — UMD/MS I/O синхронный и медленный.

**Фикс:** убрать эти `fprintf` из loop-горячего пути или загейтить `#ifdef DEBUG_VERBOSE`.

---

#### 2. `hud_init: 0.571 s` — самый тяжёлый этап загрузки

В hud_font.c функция `hud_font_init` строит **3 отдельных атласа** (размеры 9, 12, 23). Для каждой страницы:
- `malloc(px_count * 4)` — аллокация RGBA буфера
- распаковка 4bpp → RGBA8888 пиксельным циклом
- `SDL_CreateTexture` + `SDL_UpdateTexture` — GPU upload

Три размера × несколько страниц каждый = много GPU-загрузок при старте.

**Фикс варианты:**
- Объединить все страницы всех трёх шрифтов в одну текстуру-атлас при сборке
- Или кэшировать уже-распакованные данные на диске (PNG-атлас предгенерированный)

---

#### 3. `SDL_Delay(50)` во **всех состояниях** — main.c

Игровые состояния (меню, оверлеи level_complete, game_over и т.д.) тоже висят на `SDL_Delay(50)` → **20 FPS** везде. Физика игры действительно требует 20 Hz, но меню и экраны переходов не должны быть ограничены.

```c
// меню — рендерит фон, нет физики, а пауза 50ms как в игре
SDL_RenderPresent(renderer);
SDL_Delay(50);   // ← лишнее для меню
continue;
```

**Фикс:** в состояниях `APP_STATE_MENU`, `APP_STATE_LEVEL_SELECT`, etc. использовать `SDL_Delay(16)` (60 fps). Физика там не тикает.

---

#### 4. `tileset_load` (0.067 s) всегда пересобирается при смене уровня — main.c

```c
Tileset* new_tileset = tileset_load(sdl_renderer, "res/if0", theme_path);
```

При смене уровня **всегда** грузится весь тайлсет заново, даже если `theme_id` не изменился. В логе видно двойной `reload.tileset_load: 0.067 s` — это каждый `reload_level_state`.

**Фикс:** передавать текущий `theme_id` в `reload_level_state`, пропускать `tileset_load`/`bg_layer_load` если тема та же.

---

#### 5. `SDL_SetTextureColorMod` + `SDL_SetTextureAlphaMod` на каждый глиф — hud_font.c

```c
if ((int)g->page != page) {
    page = (int)g->page;
    SDL_SetTextureColorMod(rt->pages[page].tex, color.r, color.g, color.b);
    SDL_SetTextureAlphaMod(rt->pages[page].tex, color.a);
}
```

`SDL_SetTextureColorMod` — это SDL GPU state call. При отрисовке счёта (8 символов) и других HUD-текстов это вызывается когда меняется страница. Если все символы на одной странице — только 1 вызов, OK. Если страниц много — стоит кэшировать `last_color` чтобы вообще не трогать стейт если цвет не менялся.

---

#### 6. Отдельный `SDL_RenderCopy` на каждый тайл в `renderer_draw` — level_renderer.c

Для уровня 60×60 видимая зона ~30×17 = **~510 draw calls в кадре** только на тайлы (плюс foreground pass, hoops, объекты, игрок). На PSP это важно — SDL на PSP обычно реализован поверх GU, каждый RenderCopy = потенциальный flush.

**Фикс (сложный, но высокоэффективный):**  Предстроить `SDL_RenderGeometry`-batch или использовать статический `SDL_Texture` как render target для неподвижных тайл-слоёв и перерисовывать только при изменении тайла (от хупов/анимаций).
